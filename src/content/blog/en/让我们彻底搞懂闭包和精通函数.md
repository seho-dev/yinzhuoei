> When I first started learning frontend development, closures, scope, and all the rest were incredibly hard to understand. Before interviews, I could only memorize explanations, and a few probing questions would leave me struggling to explain why anything worked. I suspect many beginners have the same problems I once had, so today let's explore closures and functions together~

We actually write closures every day and benefit from them constantly. They're there in our animation logic, event callbacks, and the frameworks we use. Closures are closely tied to scope rules, so we'll cover scope along the way, too.

---

Understanding Closures

A closure allows a function to access variables outside its own body, provided those variables are in the scope where the function was declared. The declared function does not disappear when that surrounding scope finishes executing; it can still be called later.

```
var value = "我是外部变量";
```

We write code like this every day, and it is an example of a closure. Let's relate it to the definition above: the function declaration and the variable are both in global scope, and we can call testFun at any time. But an example this simple doesn't really show what makes closures useful.

When later runs and accesses value, we naturally expect that variable to have a value because it lives in the global environment. But does innerValue really become null just because its enclosing scope has finished executing? No: thanks to the closure, we can still access innerValue. That gives us this conclusion: **When we create a function inside another function, we also create a closure. That closure retains access to the variables in the scope where it was created. Even after that scope finishes executing, the closure remains, allowing us to keep accessing those variables.**

****We can illustrate this relationship with a diagram (inspired by the bubble diagram about closures in Chapter 5 of Secrets of the JavaScript Ninja).

![](http://static.yinzhuoei.com/typecho/2020/09/26/500751863420610.png)

This diagram helps explain closures. One thing to remember is that a function accessing variables through a closure has a scope chain, which retains the closure's environment information.

When we use a closure, that information stays in memory. When is it destroyed? It can be collected when the JavaScript engine determines it is no longer needed, or when the page is unloaded.

Implementing Private Variables with Closures

If you know more than one programming language, you're probably familiar with private variables. JavaScript doesn't provide them in the form discussed here, but we can use closures to create something resembling a “private instance variable.” It's not a perfect equivalent of a true private variable. Let's look at a demo.

```
function Test(){
```

```
const private = new Test();
```

The count variable inside Test is our private property. It can only be manipulated through the built-in add and get methods. We can also construct multiple instances, each with its own independent count. This is a simple example of implementing a private property with a closure: **outside code accesses or modifies the variable through inner functions, but cannot change the variable directly.**

Callbacks

When building web applications, animation requirements often involve manipulating several DOM elements and animation states at once. Before learning about closures, we might define variables in global scope, call several functions, and have each function modify the corresponding variables. That makes the code cumbersome and managing multiple variables a chore. Closures can solve this problem. Suppose we need to animate two separate areas; we could write it like this.

```
function animated(elementID){
```

If we moved tick, timer, and the other variables into global scope, animating multiple elements would require a large number of variables. With closures, each timer callback can work with its own private variables. We can therefore conclude:

> A closure is not a snapshot taken when a function is created. It encapsulates state whose variables can be modified when the function runs. As long as the closure exists, we can change those variables' values.

Tracking Code with Execution Contexts

We know JavaScript has a single-threaded execution model. We also know it has two kinds of code in this discussion: global code and function code. Accordingly, there are global execution contexts and function execution contexts. The global execution context is created when the JavaScript program starts, and a function execution context is created when a function begins executing. Let's look at an example:

```
<script>
```

When a function starts executing, a new execution context is created. When the function finishes, execution returns to the context from which it was called and continues there. To track this calling order, JavaScript uses an execution context stack, better known as the “call stack.”

![](http://static.yinzhuoei.com/typecho/2020/09/26/500771809731771.png)

(P.S. Now it's starting to click.)

> Think of plates stacked on a tray. Each plate represents a function's execution context. As functions finish, the plates are removed, until we eventually return to the global execution context.

Besides identifying the function currently executing, an execution context also lets us locate specific identifiers within the lexical environment.

---

Scope (Lexical Environments)

A lexical environment, also referred to here as scope, is an internal JavaScript engine mechanism for tracking mappings between identifiers and variables. Many articles don't make the concept clear; “mapping” is the most useful way to describe it.

Scope is closely tied to the structure of JavaScript code. Before ES6 introduced let and const, JavaScript lacked block-scoped declarations, even though developers coming from C or Java might have expected them. The most intuitive illustration of scope is nested code. Let's write an example:

```
var all = "全局的变量"
```

How does the JavaScript engine track this code and analyze its structure? That's where lexical environments come in.

An execution context has an associated lexical environment, which contains mappings for the identifiers defined within it. In this example, the for loop has mappings for a and b. Whenever a function is created, it is associated with a lexical environment, retained through its internal [[Enviroment]] property. This is an important part of how the JavaScript engine understands the relationships between pieces of code.

Now that we understand the basic rules for looking up identifiers, let's briefly review variable declarations as well, even though the basics are fairly simple.

Understanding JavaScript Variable Declarations

This is one of those questions that comes up constantly in interviews at small and medium-sized companies: what is the difference between let,

const, and var? You've probably seen it countless times, along with countless answers online. Let's summarize it using the concepts we just covered:

1. Mutability
2. Lexical environment

const cannot be reassigned.

The difference between let/const and var also lies in their lexical environments: let and const address JavaScript's lack of block-scoped declarations.

> Many experienced developers and some companies' coding standards require const in preference to var and let. A great many bugs come from mutable variables, while in day-to-day development we rarely encounter requirements that can only be implemented through reassignment. I think this is a sound idea worth encouraging.

Let's take a closer look at how const works:

We generally use const for a variable we won't reassign, or for a fixed value such as a head count or quantity used in a calculation. This also helps make JavaScript code more predictable and easier to optimize.

```
const a = "一次赋值";
```

A const declaration allows a value to be assigned only once, at initialization. Trying to assign a “new value” to that variable later throws an error. Modifying an object or array referenced by a const variable is allowed, however.

That covers mutability. Now let's look at the differences in lexical environments.

When we use var, the variable belongs to the nearest enclosing function's lexical environment, or to the global environment. Here's a demo:

```
function fun(){
```

> 1. In this example, i is declared with var, so it belongs to the nearest function's lexical environment. It therefore shares a scope with thisMessage; the for loop does not give i its own block scope.

This is why many tutorials, and much everyday code, use let for temporary variables such as loop counters. It prevents conflicts between multiple loops inside the same function's lexical environment.

Now let's rewrite the demo using let:

```
for(let i = 0; i<10;i++)
```

We can write several similar loops inside one enclosing lexical environment without conflicts, and the outer environment cannot access i.

We've covered identifier declarations and lexical environments. Next, let's dig into how identifiers are registered in those environments.

---

Registering Identifiers

If you came to JavaScript from Java or C, the following code may have puzzled you the first time you saw it.

```
var test = "我是一个测试变量";
```

![](http://static.yinzhuoei.com/typecho/2020/09/26/500772601724557.png)

Why can I execute a function before its declaration? We know JavaScript executes code line by line. Logically, if execution hasn't reached the declaration yet, calling testFun ought to be impossible. So how does JavaScript register the function and know that testFun exists?

When JavaScript creates a new lexical environment, there are two stages:

1. It visits and registers the variables and functions belonging to the current lexical environment.
2. It executes the code, with behavior depending on the declaration type and lexical environment type.

Let's examine that registration process more closely.

1. When creating a function lexical environment, JavaScript first sets up the formal parameters and their default values.

2. In a global lexical environment, it finds function declarations (not function expressions or arrow functions) and assigns each function to an identifier with the same name. If that identifier already exists, it is **overwritten**. This step is skipped for block scope in this explanation.

3. Variable declarations are registered according to their scope: var declarations belong to the function or global environment, including declarations inside nested blocks but not nested functions. let and const belong to their enclosing scope, and **block scopes register their let and const declarations**. For var, a new binding is initialized to undefined, while an existing binding retains its value.

In short: JavaScript registers identifiers according to the current lexical environment.

> This explains the apparent mystery in our earlier demo. During the first stage, JavaScript sets up the global lexical environment and assigns the function declaration to an identifier. When the second stage executes the code, that function is already available.

There's another situation we may encounter during development: a function identifier being reused.

```
console.log(typeof fun); // function
```

This involves a concept called hoisting. Function declarations are treated as if they were moved to the top of their scope, while var declarations are treated as if they were moved to the top of their function scope.

Let's analyze the code above:

1. In the first stage, the function declaration assigns the function to the identifier with the same name. When execution starts, fun therefore already has a value, and its type is function.
2. When variable declarations are processed, JavaScript finds that fun is already registered, so it does not assign undefined to it. During code execution, fun is reassigned to 3, so the second console statement prints number.

How Closures Work

We've seen that closures let us access variables in the scope where a function was created, with examples including animation logic and callbacks.

Let's revisit our earlier demos in terms of lexical environments and execution contexts. This should make closures easier to understand.

1. The private counter variable example

```
function Test(){
```

Analysis: we invoke the Test constructor using new. The addCount function exposed to the outside retains a closure. Before a call such as Test.addCount, we are in the global execution context. Calling a function creates a new execution context and a new lexical environment. The addCount environment links to the lexical environment in which that function was created. If count cannot be found inside addCount, JavaScript looks in the outer environment. Because the returned object is still active and keeps the closure reachable, count remains available. That's all there is to it…

We've now seen what execution contexts and lexical environments do. Lexical environments primarily track variables defined in functions; a new execution context creates a new lexical environment.

Remember the limitation of the private-variable approach discussed here. We can modify the demo as follows:

```
var testImport = {};
```

2. The animation example

```
function animated(elementID){
```

Analysis: calling animated twice creates two lexical environments, as well as new execution contexts. Each environment has its own elem, tick, and other variables. The code uses setInterval, and as long as a function still accesses those variables, the closure remains available, until the timer is cleared. Whenever the callback runs, the closure gives it access to the variables from the environment where it was created, greatly simplifying the code.

Summary

1. We've explored the concept of closures and used the protective-bubble analogy to deepen our understanding of lexical environments. A function retains its creation environment through its [[Environment]] property, which is why variables remain accessible after the surrounding function finishes executing.

2. The JavaScript engine tracks execution using the execution context stack, or call stack. Each function call creates a new execution context and pushes it onto the top, like the plates on our waiter's tray.

3. JavaScript uses lexical environments to track identifiers—that is, scope.

4. We can define variables at global, function, and block scope.

5. We've seen how let, const, and var differ: whether a variable can be reassigned, and whether it is block-scoped.
