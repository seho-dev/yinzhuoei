# store-persistedstate-killer

[EN](https://github.com/1018715564/store-persistedstate-killer/blob/master/README.md) / Chinese

A killer state persistence library.

---

- Persistence support for multiple libraries, including Vuex and Pinia.
- TypeScript support.
- Predefined storage drivers, including localStorage and sessionStorage, plus custom drivers.
- A relatively safer storage format, rather than plaintext.
- Flexible configuration without side effects.
- Developer-friendly state-change logs.
- Enhanced persistence features, such as renaming.

## Installation

```
npm i store-persistedstate-killer
```

## Quick Start

```ts
// main.ts
// pinia平台
import { plugins as killer, config } from \'store-persistedstate-killer\'

createApp(App)
  .use(
    createPinia().use((context) => {
      killer.pinia.init(context)
      killer.pinia.use(context)
    })
  )
  .mount(\'#app\')
```

## Design

You can bring in the plugin for each platform separately. For example, if you use Pinia, this is all you need:

```ts
createApp(App)
  .use(
    createPinia().use((context) => {
      killer.pinia.init(context)
      killer.pinia.use(context)
    })
  )
  .mount(\'#app\')
```

Each killer plugin consists of `two parts`: init and use.

## init

When the application initializes, init synchronizes the contents of storage into the store. If it finds state that exists in the store but not in storage, it synchronizes that too. This is a two-way process. The overview diagram above illustrates how killer works. From a state-management perspective, you can think of storage as a remote endpoint and their communication as `push` and `pull`.

## use

use is killer's core functionality. It listens for state changes and patch operations, synchronizing state to storage in real time.

---

As you can see, if all your application needs is to watch state and synchronize it to storage, you can use the use plugin on its own.

For more information about the platform plugins, see their specific documentation below.

## Core Modules

killer provides several core modules that power its platform plugins. Each module handles a particular concern, such as configuration, encryption, or storage.

### Configuration

killer includes a configuration that works out of the box. You can customize it for more specific needs. First, though, you should understand how the plugins work. Take Pinia as an example: Pinia consists of individual stores, each containing state, getters, and actions. The killer plugin therefore runs only after `useStore()` is called. It takes over the store's state so it can persist that state to local storage. During persistence, we may want to perform tasks such as `renaming` or `encrypting data`...

| Option | Meaning | Type | Default | Recommendation |
| --- | --- | --- | --- | --- |
| exclude | Store names to exclude | string[ ] | [ ] |  |
| include | Store names to include | string[ ] | [ ] |  |
| prefix | Prefix for storage keys | string | persistedstate-killer- | Provide a valid string |
| iv | Initialization vector used for encryption | string | \'\' | May be empty |
| isDev | Whether this is a development environment | boolean | process.env.NODE_ENV === \'development\' | Encryption is automatic when false |
| storageDriver | A predefined storage driver | defineStorageDriver | defineStorageDriver(\'localStorage\') | Accepts localStorage or sessionStorage |
| store | Detailed per-store configuration | Partial<Record<K, StoreConfig>> | No default configuration |  |
| defineStorage | A custom storage driver | setItem, getItem, removeItem, iteration | No default configuration | Use this to define a new driver if defineStorageDriver does not meet your needs |

A custom configuration in your project might look like this:

```ts
import { plugins as killer, config } from \'store-persistedstate-killer\'

createApp(App)
  .use(Router)
  .use(
    createPinia().use((context) => {
      config.defineConfig<\'main\'>({
        exclude: [\'zhangsan\'],
        include: [\'main\', \'test\'],
        isDev: true,
        storageKey: \'seho\',
        store: {
          main: {
            state: {
              hello: {
                rename: \'wuyu\',
              }
            }
          }
        }
      })
      killer.pinia.init(context)
      killer.pinia.use(context)
    })
  )
  .mount(\'#app\')
```

As you can see, killer encourages using TypeScript to configure the plugin. Pass a union type to defineConfig to declare which stores you want to work with, and you will get excellent type hints when writing the include and store options.

| Api | Desc | Type |
| --- | --- | --- |
| defineConfig | Supply configuration | [doc](https://github.com/1018715564/store-persistedstate-killer/blob/master/typings/config.d.ts) |

### Encryption

Is frontend encryption really unnecessary? Some people say so, but exposing state-management data in plaintext in localStorage does not feel ideal, even though that is what we commonly do. We need easy-to-use encryption, both for killer's internal use and as an API exposed to users, perhaps to encrypt API data or exchange sensitive information. Internally, killer uses `crypto-js`, with a default based on `browser user agent -> base64`. You can also specify a key and IV to suit your application's needs.

```ts
import { crypto } from \'store-persistedstate-killer\'

const _crypto = new crypto()
const message = \'hello, messagehello, messagehello, messagehello, messagehello, messagehello, messagehello, message\'
const encryptData = _crypto.encrypt(message)
if (encryptData) {
  const decrypt = _crypto.decrypt(encryptData)
  console.log(\'解密结果\', decrypt)
} else {
  throw Error(\'加密错误\')
}
```

You can pass a ctx object to the constructor:

```ts
const _crypto = new crypto({
  iv: \'asdasdasdasdasdasdasdasd\',
  key: \'sssaasdasdasdas234234s\'
})
```
